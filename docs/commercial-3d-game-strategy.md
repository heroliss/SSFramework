# 首款商业 3D 游戏：产品与平台策略

> 状态：**工作策略 v0.3**，更新于 2026-09-01。本文维护首款商业游戏的平台、产品定位、证据 Gate 与生产边界；当前玩法真值和第一版范围见[《游牧工坊》产品愿景与第一版地基](nomad-workshop-game-vision.md)。两份文档都是可证伪假设，不构成发布日期、销量或全平台承诺。

## 1. 执行摘要

当前建议是：

1. **Steam / Windows 首发**，采用一次性付费的单机产品；先建立商店表达、Demo、Playtest 和可构建交付闭环。
2. 产品暂名 **《游牧工坊》（Nomad Workshop）**，定位为风格化俯视角 3D、小人口、自动居民、连续旅途的移动殖民模拟。
3. 玩家不直接控制居民或驾驶车辆，而是规划设施、设置目标点与工作优先级，并处理路线、补给、维护、救援和危机。
4. 世界采用“有限种子大陆 + 连续坐标 + 稀疏兴趣点 + 局部精确模拟”，不做节点瞬移，也不承诺处处高密度或全部物件永久保存。
5. 第一版先证明游戏地基，不先生产完整商业内容：三名居民、单层移动工坊、目标点行驶、一次车外作业、基础需求与保存恢复。
6. Android / iOS 保留输入、UI、性能和存档层面的可移植性，但核心产品成立前不同时制作移动版。
7. 游戏真实使用 SSFramework 并反向暴露缺口，但不能为了展示 Framework、AI 或生成工具而牺牲玩法、审美和范围控制。

一句话产品承诺：

> **照料一群会自己生活和工作的幸存者，把一台濒临报废的荒野工程车逐渐修成家，并在一片会记住重要选择的废土上继续前行。**

## 2. 决策分层

| 层级 | 当前内容 | 变更方式 |
|---|---|---|
| 已接受方向 | 正规商业 3D 游戏；单人优先；同仓独立业务程序集；先证明核心循环 | 只有新证据表明目标不可行时调整 |
| 当前产品假设 | 《游牧工坊》；移动殖民模拟；自动居民；目标点行驶；Steam / Windows 付费单机优先 | 通过灰盒和目标玩家证据继续收窄，不把讨论稿当最终 GDD |
| 第一版边界 | 单层 2.5D 建造、一个原型区域、三名居民、少量资源与设施、一次完整旅途和车外作业 | 不依赖正式美术和大量内容，先验证是否值得进入垂直切片 |
| 有意延后 | 多地貌、心理与关系、商人/难民/势力、战斗、前哨网络、生态修复、最终故事和完整资产管线 | 第一版通过后按最高风险逐项进入 |
| 当前不做 | 手动驾驶、直接控制居民、可行走多层甲板、无限开放世界、多人、UGC、LiveOps、运行时生成式 AI | 只有真实产品证据证明必要时重新评估 |

规则是约束当前投资，不是不可反思的教条。发现玩家体验、技术原型或市场证据与规则冲突时，应说明观察、替代方案和影响，再修改本文。

## 3. 目标玩家与差异化

优先面向喜欢以下体验的 Steam 玩家：

- 喜欢殖民模拟、资源链、空间布局和“看着系统自行运转”的满足感；
- 愿意关心少量有名字、有需求和性格的居民，而不是管理数百人的统计表；
- 喜欢旅途、探索、维修和艰难取舍，希望自己的决定在世界中留下痕迹；
- 能接受暂停与加速并存的中长时单机体验；
- 喜欢风格化、可读性强、有温度的微缩 3D 世界，不要求写实 AAA 画面。

当前差异化不是“把几款殖民模拟功能相加”，而是以下组合：

1. **基地持续移动**：居民生活、设施状态和资源消耗不会在旅行时冻结。
2. **小人口共同体**：成熟常驻规模约 8–12 人，每个新成员同时带来能力、需求和关系。
3. **自由目标而非路线节点**：玩家在连续世界中设置任意目标，可以中途停车和改道，但不亲自驾驶。
4. **车上与车外共用一套系统**：外部采集、建设、修复和防御都消耗同样的人员、时间、物资和能源。
5. **重要后果持久化**：车辆伤痕、主要地点、前哨和人物去向形成这局独有的旅行历史。

## 4. 平台策略

### 4.1 平台顺序

| 平台 | 当前角色 | 进入条件 |
|---|---|---|
| **Steam / Windows** | 首发目标 | 第一版循环成立后建立 Windows Build Profile、可分发 Player 包和商店表达验证 |
| **Steam Deck** | 次级兼容目标 | 垂直切片在键鼠与手柄上成立后，以真实设备或可靠环境验证，不提前承诺认证 |
| **Android / iOS** | 后续产品分支 | 通过独立移动 Gate，证明触控、会话、性能、商业模式和维护成本成立 |
| 主机 | Later | PC 产品证据、资源和发行合作成立后另立项目 |

### 4.2 为什么不同时做 PC 和手机

Unity 能切换平台，不代表产品可以无成本移植。移动殖民模拟仍需重新验证：

- 建造、选择居民、查看任务阻塞和大地图在触屏上的信息密度；
- 6–7 英寸屏幕上的字号、遮挡、安全区和镜头缩放；
- 短时中断、后台恢复、耗电、热降频、内存和安装包；
- 付费单机与 IAP / 广告 / 长线留存之间不同的产品结构；
- iOS 的 Xcode / macOS 构建链和两家商店的账号、测试、隐私与审核要求。

因此采用“**产品单平台，架构可移植**”：业务核心不依赖 Steam API；输入使用 Action 层；UI 不写死分辨率；存档和平台服务藏在接缝后；性能预算从第一天记录。但在移动 Gate 前，不制作触控专用 UI、不接广告或 IAP SDK，也不维护第二套产品。

## 5. 从地基到商业产品的证据 Gate

### Gate 0：玩法假设能被复述

产物：当前愿景文档、核心循环图、一段开局与一段中期玩法 Storyboard、少量同类型产品拆解。

通过信号：目标玩家在不听 Framework 和 AI 介绍时，能够复述“管理自动居民、修复移动家园、设定目标探索废土”，并主动提出自己想做的选择。若只能复述世界观而说不出行为，应先改玩法表达。

### Gate 1：Foundation Prototype 值得继续

产物：[第一版地基](nomad-workshop-game-vision.md#8-第一版foundation-prototype-v01)定义的 30–45 分钟灰盒。

通过信号：自动居民可理解；目标点旅行不是动态壁纸；车上建造与车外作业互相影响；保存和返回主要地点可信；试玩者能说出下一步想修复、扩建或探索什么。

### Gate 2：核心循环与镜头成立

产物：扩大到一段连续的开局旅程，加入一项有辨识度的居民差异、一条维护链、一个重大遭遇和一套候选镜头/建造表达。

通过信号：玩家不用直接操控角色仍保持决策密度；单层建造容量足够且可读；自动 AI 的失败能够解释；增加内容没有把循环拆成互不相关的小游戏。

### Gate 3：资产管线与风格可持续

产物：一个英雄级车辆模块族、代表性居民、环境模块族、材质、关键 VFX / SFX，并全部进入真实镜头。

通过信号：风格统一；拓扑、UV、碰撞、LOD、动画、材质、命名与授权可追溯；修改成本可接受；目标机达到临时性能预算。

### Gate 4：垂直切片是一个产品

产物：可从标题玩到自然阶段目标的连续切片、Windows 包、设置、暂停、存档、教程、基础分析事件、试玩记录、截图和真实 Gameplay 素材。

通过信号：陌生玩家无需开发者陪同即可开始、理解和继续；核心缺陷主要是可迭代的平衡与表达，而不是“不知道为什么要玩”。

### Gate 5：商业表达与内容生产成立

产物：Steam Coming Soon 页面、Gameplay Trailer / GIF、Demo 或 Playtest、明确标签和语言计划，以及可持续的内容吞吐量。

通过信号：商店页面和试玩产生高质量外部反馈；玩家数据支持继续生产。参加 Steam Next Fest 前必须有足够成熟的 Demo，每款游戏只能参加一次，不能仓促消耗机会。

## 6. AI、生成资产与 Harness

AI 用来加速搜索、比较、草图、变体、代码、测试、重复操作和证据整理；Art Direction、最终资产选择、玩法取舍、玩家反馈解释、商业授权和发行责任仍由人承担。

建议生产链：

```text
玩家目标 / 产品假设
  → 可审查的设计或资产 Brief
  → 人工、生成工具或混合制作
  → DCC / Unity 规范化
  → 运行时、视觉、性能与授权验收
  → 真实玩家反馈
  → 保留、返工或删除
```

候选工具和成熟度沿用 [AI 游戏开发能力图谱](ai-game-development-capability-map.md)；音效和音乐按 [AI 音乐与音效生产候选](ai-audio-production-research.md)做小规模 Spike。探索阶段不急于编写平台安装指南或绑定 Skill；只有流程稳定、重复使用且授权边界清楚后再产品化。

游戏级 Harness 首先覆盖：

| 层 | 第一批证据 |
|---|---|
| 规则与经济 | 固定 Seed、资源守恒、任务预留、需求和磨损边界 |
| 世界与存档 | 区块重建、分级持久化、保存/读取往返和版本兼容 |
| 玩家路径 | 真实 Input Action 驱动“开局 → 修车 → 设目标 → 停靠 → 重新启程”PlayMode smoke |
| 视觉 | 固定镜头、底盘尺寸、屋顶/剖面方案和提示遮挡截图 |
| 性能 | 居民数量、区块流送、时间加速和目标 Player Build 的 CPU / GPU / GC / 内存预算 |
| 体验 | 观察玩家、访谈和问题严重度；自动测试不能证明好玩 |

任何随游戏发布且使用生成式 AI 制作或实质改造的图片、模型、纹理、音频、文本或本地化，都应记录工具、版本、日期、Prompt / Seed、输入权利、许可证、人工修改与最终用途。首款游戏默认只使用预生成、可人工审查、可替换的内容；运行时生成不是需求。

## 7. 仓库与 Framework 边界

正式开始第一版时使用暂定目录，产品名确认后再一次性命名：

```text
Assets/Game/NomadWorkshop/
├── Runtime/
├── Editor/
├── Tests/EditMode/
├── Tests/PlayMode/
├── Content/
└── Settings/
```

- 游戏拥有独立 asmdef，只消费 Framework 公共 API，不复制 Framework 源码；
- 游戏专属的居民 AI、世界流送、设施、内容、UI 和资产工具留在游戏目录；
- 只有第二次出现、跨游戏成立，或确实阻断公共用法的缺口才回流 Framework；
- 回流时按风险决定 Interface、测试、Demo、guide 或 ADR，不为形式完整机械上提；
- 重复的 AI 操作流程再形成 Project Skill / Harness，确定性门禁优先落入测试或工具；
- 产品文档可以继续迭代，重大方向变化需同步本文、游戏愿景和路线图。

## 8. 主要风险与提前终止信号

| 风险 | 提前信号 | 应对 |
|---|---|---|
| 自动化缺少参与感 | 玩家设置目标后长时间只等待 | 增强策略、优先级与可预见压力；不靠手动控制掩盖 AI 或节奏问题 |
| 居民行为不可信 | 玩家经常不知道为什么无人工作 | 把任务阻塞、预留、路径和需求做成可查询的一等状态 |
| 世界规模反客为主 | 大量工作用于生成空地和保存小物件 | 限制第一版区域，持久化分级，兴趣点提供内容密度 |
| 单层容量不足 | 为放设施持续扩大底盘，居民和状态不可读 | 用挂点、升级、多用途设施和车外产能解决；只做有限扩建 |
| 系统堆砌 | 贸易、塔防、生态和关系各自像另一款游戏 | 所有系统必须改变同一套人员、时间、资源、车辆和世界状态 |
| AI 资产风格泛化 | 单件好看，放入同一镜头像多个游戏 | 先做 Art Bible 与模块族，英雄资产人工精修，不合格结果可替换 |
| Framework 反客为主 | 里程碑以新公共模块数量汇报 | 游戏侧先解决；达到跨项目证据后再抽象 |
| 过早多平台 | PC 地基未成立就制作触控和商店 SDK | 移动工作必须经过独立 Gate |
| 太晚面对玩家 | 大量内容完成后才发现循环难理解 | Gate 1 起进行少量目标玩家观察，逐步扩大样本 |

## 9. 近期工作顺序

1. 继续用具体开局和中期场景检验[当前玩法愿景](nomad-workshop-game-vision.md)，只解决会改变地基的产品问题。
2. 用灰盒镜头 Spike 比较开放甲板、自动隐藏屋顶和剖面车厢，确认单层建造与居民可读性。
3. 建立最小游戏程序集和 Foundation Prototype，只实现 v0.1 内容上限。
4. 用固定 Seed、保存往返、AI 长跑和真实 Input 路径建立第一条游戏 Harness。
5. 让少量目标玩家在无人讲解下试玩，依据等待时间、理解、主动目标和错误归因决定保留、重做或停止。
6. 地基通过后才进入性格、维护、商人/难民、多地貌、前哨、战斗和正式资产生产。
