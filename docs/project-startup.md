# 新项目准备与初始化规划

类型：方案；状态：**Proposed**；范围：消费工程初始化流程。收尾条件：初始化能力经过真实消费工程验证后，将已实现的用法合入接入指南与工具说明，重要设计取舍留在 ADR，移除已完成的方案正文。生命周期见[文档索引](README.md#文档生命周期与-ai-阅读范围)。

本文区分当前能力、推荐的项目组织方式和后续初始化工具规划。目录是参考结构，不会因安装 Framework 自动生成；本文也不声明已经提供项目模板或中文字体包。

## 当前已经提供什么

| 项目 | 当前状态 |
|---|---|
| Git 配置 | 仓库根目录有 `.gitignore`、`.gitattributes`，作用于 Framework 仓库；UPM 安装不会把它们应用到消费工程根目录 |
| 第三方包源 | `Tools~/Setup-SSFramework` 提供预览、合并和备份；原 `Configure-OpenUPM` 保留为只配置包源的入口 |
| 文档与协作规则 | 包内有 API、ADR、模块地图与维护用 AGENTS.md；不是消费工程的项目文档或根 AI 规则 |
| 项目目录 | guide 有按特性组织的参考结构；没有一键创建整个游戏工程的工具 |
| Framework 配置资产 | 工具按类型发现；显式创建新配置时默认使用 `Assets/Settings/SSFramework`，不要求已有资产迁移 |
| 中文 / CJK 字体 | 有 fallback 链、locale 档案类型和字集生成器；无字体源、预生成字体资产或默认接线 |
| Unity MCP | 外部接入工具可选 AnkleBreaker / Coplay，默认生成手动指引，也可将所选包加入工程清单；服务端和客户端连接由使用者配置 |

## 初始化流程与后续工作

包源和可选 MCP 的清单配置已实现，用法统一维护在[接入工具说明](../Tools~/README.md)。当前工程模板、字体资源与运行时模块选择仍属以下规划，MCP 在具体工程中的连接、编译与构建也需单独验收。

在现有外部接入工具与包内 Editor 工作台之间划分职责，由一个可理解的流程呈现：

1. **安装前**：检查工程版本、预览并配置包源，按需提供消费工程的 Git / 文档 / AI 规则模板。
2. **安装后**：通过 Unity Editor 创建资产目录与 meta、业务 asmdef、Framework Profile 及可选字体资产；不手写场景、Prefab 或字体资产 YAML。
3. **验收**：检查依赖 revision、编译、最小启动场景、文字显示、Play 生命周期及目标 Player 构建。

模块选择应显式显示，例如 Git 配置、参考目录、文档与 AI 规则、入门字体。默认不覆盖已有文件；冲突先展示，重复运行不制造重复目录或修改用户已维护的规则。包升级也不自动重写消费工程模板。

### 依赖与可选能力

选择器先区分编译所需依赖、功能模块和开发工具，展示每项引入的包、固定版本、工具环境及修改位置。

| 类别 | 推荐交互 | 当前边界 |
|---|---|---|
| 核心依赖 | 随核心自动解析，不让使用者逐项猜测 | Core 直接引用 UniTask、R3；这些依赖不能随意取消 |
| 功能模块 | 按资源、配置、热更、UI 等用途选择，并自动计算依赖闭包 | 当前 Framework 仍是单一 UPM 包，根 `package.json` 的依赖无条件解析；尚未提供可独立安装的模块组合 |
| 开发工具 | Unity MCP 等由使用者选择；同一工程先采用一个 MCP 提供方 | MCP 清单配置和手动指引已提供，不成为 Framework 运行时依赖；工具环境、编译与连接单独验收 |
| 项目资源与模板 | 字体、Git 配置、目录与 AI 规则分别选择，应用前预览 | 按需安装资源与合并模板，不在每次包升级时重写项目文件 |

功能模块的“可删除”结构不等于已经实现“UPM 可选安装”。实现选择器之前，必须让所选源码、asmdef、测试与包清单保持一致，验证移除模块后仍能编译、测试和构建；`autoReferenced:false` 不会停止程序集编译。当前依赖与删除边界见[模块地图](framework-module-map.md)及[接入指南](consuming-framework.md)。

Unity MCP 接入的三个步骤与工具边界已转入[接入工具说明](../Tools~/README.md#mcp-环境与连接)，后续工具扩展仍复用该流程与[自动化接入验收](unity-mcp-tips.md#可选-mcp-接入与验收)。提供方、服务端和客户端配置保留在消费工程的开发工具边界内。

### Git 模板

值得提供专用于消费工程的模板，而不是直接复制 Framework 仓库的简化配置：

- `.gitignore` 排除 Unity 缓存、本机编辑器数据、IDE 产物、构建输出和测试临时文件，保留 `Assets` 及 meta、`Packages/manifest.json`、`packages-lock.json`、`ProjectSettings`。
- `.gitattributes` 统一源码、JSON、Unity YAML 的文本处理与换行，保留二进制资产的二进制语义。
- Git LFS 与 Unity YAML Merge 作为独立选项，检查所需工具和仓库配置后启用。模板不默默建立新的 LFS 服务依赖或覆盖已有过滤器。
- AI 工具本机状态、访问凭据和未经筛选的日志不进入项目共享规则或版本库。

### 可选中文字体资源

推荐先提供一个明确覆盖范围的简体中文 Regular 入门资源，其他字重及繁体中文、日文、韩文按 locale 扩展。Noto Sans CJK / 思源黑体是可评估来源；分发时固定来源与版本，随资源保留对应许可与版权声明。参考 [Noto CJK](https://github.com/notofonts/noto-cjk) 和[许可原文](https://github.com/notofonts/noto-cjk/blob/main/Sans/LICENSE)。

交付内容应包括字体源、适配所选 UI 后端的字体资产、缺字验证文本、fallback 接线说明及来源记录。TMP 与 TextCore 资产分别处理；动态图集依赖的字体源应保留。不能把常用字裁剪集称为“完整中日韩兜底”，也不能保证开发机可用的系统字体在玩家设备上存在。

资源可以由初始化入口按需安装独立字体包。若先采用 UPM `Samples~` 分发，必须说明它只是按需导入：Git 获取主包时仍会下载其中的字体文件。字体源的下载体积、图集显存和最终 Player 包体分别验收，不混为同一指标。

## 消费工程参考结构

按实际模块逐步建立，不一次生成大量空目录。游戏资产移动和目录创建应由 Unity 完成，以保留 GUID。

```text
Project/
  README.md                   # 如何打开、运行、测试、构建
  AGENTS.md                   # 简短项目协作入口与文档索引
  .gitignore
  .gitattributes
  docs/
    README.md                 # 当前指南、方案与证据的导航；按任务读取
    overview.md               # 目标平台、玩法范围、术语、首个里程碑
    architecture.md           # 模块依赖、状态所有权、生命周期
    development.md            # 环境、生成、测试和调试流程
    performance.md            # 最低目标硬件、场景规模与测量方式
    release.md                # 构建、资源版本、存档兼容与验收
    adr/                      # 重要决定及理由
  Assets/
    Game/
      Bootstrap/              # 项目启动与组合
      Common/                 # 已有多个模块确实共享的内容
      Features/<Feature>/    # 特性代码、UI、Prefab 和配置
      Simulation/             # 可选：独立的仿真数据与系统
      Editor/                 # 项目专属编辑器工具
      Tests/                  # 项目测试与明确的测试程序集
    Settings/                 # 渲染、输入和其他项目配置
      SSFramework/            # 工具显式创建的 Framework 配置
    ThirdParty/               # 未由 UPM 管理的第三方资源与许可
  Packages/
  ProjectSettings/
  Tools/                      # 项目构建、检查与生成脚本
```

目录不等于程序集边界。asmdef 应按依赖和职责建立，业务显式引用需要的 Framework 程序集；Editor / Tests 与运行时分开。仿真状态只由一个明确的模块持有，UI 读取快照或只读状态。热更与 AOT 的划分另行验证，不按文件夹名推断。

## AI 规则应记录什么

根 AGENTS.md 保持简短：项目版本与入口、重要文档位置、真实可执行的测试 / 构建命令、资产与 PackageCache 修改边界，以及提交检查要求。具体模块有额外约束时，再添加局部规则。

不要把包内维护规则整份复制成游戏规则；游戏需要自己的目标与约束。对 Framework API 使用版本对应的文档链接，避免复制后漂移。不要在规则中宣称不存在的测试或已过时的架构是当前事实；计划与已实现内容明确分开。

参考[文档生命周期](README.md#文档生命周期与-ai-阅读范围)，只在事项值得长期保留时建文档。新工程可以先把少量概览、开发步骤和性能目标写在 README，内容增长后再拆成上述文件；不必预先填满所有目录。临时准备清单完成后，将实际采用的设置合入当前说明，取舍放入 ADR，移除过期清单。

## 开发前优先明确的事项

| 事项 | 最小可检查结果 |
|---|---|
| 产品范围 | 目标平台、镜头与操作方式、核心循环、首个可玩闭环 |
| 画面预算 | 渲染管线、最低目标显卡、分辨率、灯光 / 阴影与材质预算 |
| 仿真预算 | 实体规模、更新频率、暂停 / 倍速策略、CPU 与 GC 测量场景 |
| 输入与 UI | Action Map、改键保存、UI 输入隔离、中文显示与不同分辨率 |
| 状态与存档 | 稳定对象标识、保存格式版本、加载恢复、迁移与失败处理 |
| 内容生产 | 配置数据、资源地址、生成代码所有权、第三方来源与许可 |
| 工程验收 | 干净检出后可安装、无编译错误、关键测试通过、目标 Player 可运行 |

初始化工具只能建立基础文件与配置；这些游戏决策和验收结果仍需由项目逐项落实。现有 API 和安装方式见[接入与升级](consuming-framework.md)及[框架指南](framework-guide.md)。
